# 架构与安全设计

这份文档记录**为什么这么设计**，尤其是几个看起来多此一举、其实是刚需的约束。

## 1. 三个世界的边界

Chrome 扩展有三种执行环境，能力完全不同：

| 环境 | 例子 | 能用 `chrome.*` 吗 | 页面能访问吗 |
|------|------|------------------|-------------|
| 主世界（MAIN） | 页面自己的 JS | ❌ | ✅ |
| 隔离世界（ISOLATED） | content script | ✅ | ❌ |
| Service Worker | 后台 | ✅ | ❌ |

页面的 JS 拿不到 content script 的变量，content script 也拿不到页面的变量。
唯一的公共地带是 `window`（两个世界共享同一个 window 对象，但 JS 上下文隔离），
所以只能靠 `window.postMessage` 通信。

于是数据流是：

```
页面脚本                content script            service worker            服务端
window.sqlext.parse  →  postMessage  →  chrome.runtime.sendMessage  →  fetch
       ↑                                                  │
       └────────────  postMessage  ←──────────────────────┘
```

`src/content/page-bridge.js` 跑在主世界，暴露 `window.sqlext`；
`src/content/host.js` 跑在隔离世界，负责注入前者并转发消息。

## 2. 令牌绝不能出扩展

`chrome.storage.local` 里的登录令牌，只有 service worker 读得到。
主世界的页面脚本能拿到的东西**只有解析结果和错误信息**。

如果把令牌放进 `window.sqlext`，等于把用户的账号交出去了——
页面上任何一段第三方脚本（统计、广告、SDK）都能读到。

## 3. 最重要的一条：按站点授权

**如果不做这层，任何网站都能白嫖用户的余额。**

设想一下没有授权机制：用户在某个网站的页面上打开控制台，
或者更糟——那个网站自己就有脚本，它悄悄调用 `window.sqlext.parse(...)`，
用光用户的积分。人是你，账是你付，锅是用户背。

三层防线：

1. **内容脚本只注册在已授权的站点上**（`chrome.scripting.registerContentScripts` 动态注册），
   未授权的站点里 `window.sqlext` 压根不存在。
   不用 manifest 里的 `<all_urls>`，装插件时也不申请"读取所有网站数据"权限——
   商店审核友好，隐私上也说得过去。
2. **service worker 再查一遍授权**：即使内容脚本被误注入，
   service worker 也会拒绝未授权站点的请求（`site_not_authorized`）。
3. **服务端再查一遍**：授权信息存在服务端，跨设备同步，
   插件被绕过也拦得住。

授权必须由用户在扩展页面里点「允许」——`chrome.permissions.request()`
必须在用户手势里调用，而且第一个 `await` 之前就要调（手势会被消费掉）。

## 4. 为什么解析逻辑放服务端

好处：

- 解析能力更新不用重新发版、过商店审核
- 解析逻辑（尤其是"怎么从 SQL 里抠出表名"这种容易踩坑的规则）集中在一处，
  客户端不需要跟着升级
- 计费在服务端，客户端改不了

代价（**这是真实存在的风险，必须正视**）：

Chrome Web Store 的 MV3 政策要求"完整功能必须能从提交的代码里清楚看出来"，
且"外部资源不得包含逻辑"。一个纯转发的薄壳是最容易被质疑的形态。

对冲办法：

- 扩展里保留**实质性功能**：账号管理、余额、订单、站点授权、参数校验、
  速率限制、日志——这些都在客户端
- 服务端返回的是**数据**（JSON），不是"要执行的代码"，不违反远程代码禁令
- 商店描述里写清楚"本扩展调用我们的解析 API"，并提供 API 文档链接
- 如果审核仍然不过，退路是**自建分发**（企业策略 / CRX 自签名 / 内部使用）

## 5. 计费顺序：先扣后算，失败退费

```
余额不足 ──────────────→ 402，不解析
       ↓ 扣费
    解析 SQL
       ├─ 成功 → 返回结果
       └─ 失败 → 退费 + 400
```

先扣后算是为了不给"并发刷"留窗口：先算后扣的话，
20 个并发请求能同时通过余额检查，把 1 积分的余额刷出 20 次解析。

失败退费是因为"扣了钱没结果"是最容易引发纠纷的组合。

## 6. 令牌用随机串而不是 JWT

JWT 无状态、免存储，但**吊销不了**。插件是长期装在用户浏览器里的，
用户换机、封号、退款之后，必须能立刻让旧令牌失效。

随机 32 字节 + 服务端存储，吊销就是删一行记录。

口令用 bcrypt（`golang.org/x/crypto/bcrypt`），登录失败时不区分
"用户不存在"和"口令错"，避免枚举注册过的邮箱。

## 7. 存储抽象

`store.Store` 是接口，目前只有内存实现。生产环境换成 MySQL 只需实现这个接口，
订单/余额/会话的逻辑都在上层，不用动。

内存实现的取舍很明确：**开发、自用、内网够用，重启即丢余额**。
真要上线收费，第一件事就是把它换成 MySQL。
