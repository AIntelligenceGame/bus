# 市场调研

做这个插件之前，先弄清楚三件事：**谁会买、有没有现成竞品、能不能过审变现**。

## 1. 谁会用

**技术受众比想象的大。** 这个插件服务的不是"普通用户"，而是每天要读 SQL 的人：

| 角色 | 场景 | 痛点 |
|------|------|------|
| 后端 / DBA | 慢日志里一堆语句，要看清涉及哪些表、哪些字段、怎么关联 | 手工拆 SQL 慢；一张大查询涉及 10 张表时肉眼很难理清 |
| 数据分析师 | 拿到同事给的 SQL，想知道它到底查了什么 | 不知道有没有 join、有没有 N+1、有没有全表扫 |
| 前端 / 全栈 | 在浏览器控制台/调试工具里看到 SQL | 想在网页上一键结构化 |
| 客服 / 售前 | 客户报了个 SQL 报错，粘贴到工具里分析 | 需要一个"发个链接就能用"的轻量工具 |

**最直接的场景就是你提到的慢日志解析**：运维把慢日志里的语句贴到某个网页上，插件解析出表/字段/索引，辅助判断"这条慢查询命中了哪个索引"。

## 2. 竞品：这条路上已经有谁

| 产品 | 形态 | 覆盖 | 判断 |
|------|------|------|------|
| [MySQL Slow Log Analyzer](https://github.com/davydmaker/mysql-slow-log-analyzer) | 纯前端网页（拖日志文件进去） | MySQL/MariaDB 慢日志、severity 分类、聚合统计 | **最接近的替代品**，但它是"拖文件进去分析整个日志"，不是"嵌在别人页面里调接口" |
| [SlowLogAnalyzer](https://saasbrowser.com/en/saas/1625620) | 网页 + WASM | 声称能处理 2GB+ 日志、百万级查询 | 性能路线 |
| [EverSQL 扩展](https://www.ilovechrome.com/zh-cn/extension/amihcpfgniggncfcljabdgcdbccbpiin/) | Chrome 扩展 | 把慢查询发给 EverSQL 做索引优化 | 只有 ~881 安装；Manifest V2（已被 Chrome 淘汰）；只支持 MySQL/PG |
| [Foglight 扩展](https://blog.quest.com/product-post/say-goodbye-to-sql-blind-spots-meet-query-explorer-in-foglight) | Chrome 扩展 | 在任何网页里选中 SQL 丢给 Foglight 分析 | 商业产品，绑定 Foglight 生态 |
| SQL Formatter 类扩展 | Chrome 扩展 | **只做格式化美化** | 用户量普遍很小（20–25 安装量级），说明"纯工具型小插件"靠商店自然流量很难起量 |
| [Avanty](https://aitools.fyi/compare/sqlflash-vs-avanty) | Chrome 扩展（Metabase 内） | 自然语言生成 SQL + 解释 | 垂直场景 |

**结论**：

1. **"把 SQL 解析成结构化数据"这件事本身没人做好**。要么只做格式化（太浅），要么绑死在某个商业产品上。
2. **纯插件靠商店自然流量很难**——SQL Formatter 那类只有几十个安装。这意味着**你的推广渠道不能只靠商店**，需要自己导流（把工具做成网页、SEO、嵌进已有的运维社区）。
3. **你的差异化点在"嵌进别人的页面"**——上面所有竞品都是"你把东西拖进我的页面"，你是"我的页面直接调你的接口"。这是 Foglight/EverSQL 的路子，但它们是给自家产品导流的。

**这直接决定了一个产品决策**：光有插件不够，**要配一个网页版**（用户不用装插件也能用），插件是"深度集成"的入口，网页是"拉新"的入口。两者共用同一个 `sqlextd` 服务端。

## 3. Chrome Web Store 政策：两个真实风险

### 风险 A：MV3 的"远程代码"禁令

[MV3 政策](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)要求：

> 完整功能必须能从提交的代码里清楚看出来；外部资源**不得包含逻辑**。

但[程序政策](https://developer.chrome.com/docs/webstore/program-policies/policies)同时**明确允许**扩展与远程服务器通信，用途包括：同步用户账号数据、拉远程配置（**前提是逻辑留在包里**）、拉非逻辑资源（图片）、服务端操作（比如用私钥做加密）。

**对本项目的判断**：服务端返回的是 **JSON 数据**（解析结果），不是"要执行的代码"，所以不构成"远程代码"。但**"纯转发的薄壳"是最容易被质疑的形态**——审核会问"这个扩展自己做了什么"。

**对冲**：

- 扩展里保留**实质功能**：账号管理、余额、订单、站点授权、参数校验、速率限制、错误处理
- 商店描述写清楚"本扩展调用我们的 SQL 解析 API"，并给出 API 文档
- 审查不过的退路：**自建分发**（企业策略推送 / CRX 自签名 / 打包给内部用户），不做公开商店

### 风险 B："任意网站都能调用我的付费接口"

这是**比审核更严重的问题**——是产品级的安全漏洞。

没有授权机制的话：任何网站都能在自己的脚本里偷偷调 `window.sqlext.parse(...)`，烧掉用户的积分。**人是你，账是你付，锅是用户背。**

本项目的三层防线（详见 [architecture.md](architecture.md)）：

1. 内容脚本**只注册在已授权的站点**（`chrome.scripting.registerContentScripts` 动态注册），
   没用 manifest 里的 `<all_urls>`——装插件时不申请"读取所有网站数据"权限，审核友好
2. service worker 再查一遍授权
3. **服务端再查一遍**——扩展能被绕过，服务端是最后一道闸

`chrome.permissions.request()` 必须在**用户手势**里调用，且第一个 `await` 之前就要调（手势会被消费掉），否则静默失败。

### 顺带：不要用 `<all_urls>`

用 `optional_host_permissions` + 动态注册，既避免审核红旗，也避免用户看到"读取和更改您在所有网站上的数据"这种吓人的权限提示。

## 4. 变现模式

[Chrome Web Store 的内置支付在 2020/2021 年被彻底废弃](https://addonpay.com/deprecated-chrome-web-store-payments-what-to-use)：2020-09-21 停止新项目，2021-02-01 停止存量项目。**商店现在只是分发渠道，账单、授权、税务全要自己扛。**

2026 年还在用的模式：

| 模式 | 适合度 | 说明 |
|------|-------|------|
| **Freemium** | ⭐⭐⭐⭐⭐ | 免费额度 + 付费墙。转化率通常 0.5%–2% |
| **积分充值（Pay-Per-Use）** | ⭐⭐⭐⭐⭐ | **本项目就是这个**。适合"调用有成本的外部 API"（AI、翻译、存储） |
| **订阅** | ⭐⭐⭐ | 基础订阅 + 额度包的混合定价最稳，能对冲 API 成本波动 |
| 一次性买断 | ⭐⭐ | 只适合没有服务端成本的产品（纯格式化插件） |
| 广告 | ⭐ | RPM 低；且**不得出售浏览数据**用于个性化广告 |
| 联盟返佣 | ⭐ | 必须在商店页和扩展内**明确披露**；2025-06-10 起强制执行 |

**本项目选「积分充值」是对的**：解析跑在服务器上，有真实成本（带宽、CPU），按次计费天然对得上。

## 5. 支付方案

### 5.1 三个绕不开的约束

**约束一：插件本身不能收款。** Chrome Web Store Payments（商店内原生收费/订阅）
2020-09 禁止新建付费插件，2021-02-01 完全停止收费，已彻底弃用。商店只做分发。
所以"插件内充值" = 你必须有自己的 **Web 收银台**，插件只是入口。
**这意味着你的域名和网站要面对 ICP 备案 + 支付渠道的主体一致性校验。**

**约束二：微信支付的开发者接口几乎都要求经营主体。** 微信官方入驻主体类型是企业、
个体工商户、党政机关/事业单位、民非、社会团体、基金会，**均需营业执照**；
小微商户（个人、无执照）只能拿到**静态/动态收款码**——没有回调、没有 API。
**没有营业执照的个人，今天拿不到能自动回调的 Web 收款接口。**

**约束三：中国大陆主体开不了 Stripe。** Stripe 官方支持列表里没有中国大陆
（页脚明确写 "not available in mainland China"），没有真实境外主体就没有原生 Stripe 账户。

### 5.2 方案对比（按落地难度排序）

| # | 方案 | 资质要求 | 工作量 | 费率 | 关键风险 |
|---|------|---------|-------|------|---------|
| **0** | **人工转账 + 管理员加余额** | 身份证 + 一个个人收款码，**零资质** | 0.5–1 人天 | 0% | 限额、无回调、对账全靠人眼、税务 |
| **1** | **支付宝个人账号 + 当面付/电脑网站支付** | 支付宝实名（个人）+ **网站 ICP 备案**（个人主体免费 3–7 天，主体须一致）；营业执照可选 | 5–7 人天 | 0.6% | 无执照则单笔 ≤2000 / 单日 ≤20000；网站未备案会被拒或限权；30 天试用到期未补资料即停用 |
| **2** | **个体工商户 + 微信 Native + 支付宝 PC** | 营业执照（政府收费全免，线上 1–3 工作日）+ 域名备案主体是该个体户 | 10–15 人天 | 0.6%（个体户微信约 0.54%） | 备案主体与商户主体不一致（最常见）；年维护 3000–6000 元（代账 + 地址挂靠） |
| **3** | **微信小程序个人主体虚拟支付** | 个人身份证 + 小程序认证 + 类目含「工具」+ 小程序备案（**7–20 工作日，须提前 30 天启动**） | 3–5 人天（还要多做一个小程序） | Android 1% / **iOS 12%** | **月 10 万封顶**；iOS 回款 45–60 天；2026-04-01 起虚拟商品外跳收款即下架 |
| **4** | **Paddle（海外 MoR）** | 护照 + 地址证明 + 含 ToS/Privacy/Refund 的落地页 + **企业域名邮箱** | 6–8 人天 | 5% + $0.50 | 中国用户卡支付失败率高；订阅不支持支付宝/微信；MoR 平台自身有破产风险 |
| — | 收付通 / EDI 平台 | **公司主体 + ICP 证(B25) 或 EDI(B21)**，个体户不受理 | — | 0.6%+ | **单人不可行**，只有做成"多人卖插件、平台抽成"才需要 |

### 5.3 明确不要碰的

| 方案 | 判定 | 理由 |
|------|------|------|
| 自建彩虹易支付/"免签约支付"接真实资金 | **刑事风险** | 无牌照无备案，可能构成**二清**与非法经营。"海草生活"App 案已有主犯因非法经营罪判 5 年 6 个月至 2 年 6 个月；上游通道一关即断；跑路历史密集（菜信商圈、丫丢丢） |
| 个人收款码 + 监听到账短信做自动回调 | **灰色，随时封禁** | 违反支付平台规则与央行 259 号文；异地高频风控；无订单号无对账 |
| 用**别人/别家**的收款码收款 | **帮信罪** | 出借 3 个以上对象或结算额 20 万+/违法所得 1 万+ → 3 年以下；账户冻结 + 征信污点 |
| 无营业执照申请微信 Native/JSAPI | **系统层面不可行** | 微信入驻主体类型不含小微 |
| 个人支付宝给经营性网站接支付但不备案 | **高风险** | 支付宝要求网站已 ICP 备案且主体一致；境外/香港服务器无法备案 |

### 5.4 三件从第一天就要做对的事

1. **资金尽量直达你自己的账户**——自有商户号 / 自有 Paddle 账户，不让第三方过手。
   判断服务商是否合规只有三条：**能否自己登录商户平台、结算账户名是否与你的营业执照一致、
   合同是否写明资金不经手**。
2. **每天跑一次官方账单 diff**（微信交易账单 / 支付宝 `bill.downloadurl.query`）做掉单兜底。
   支付宝当面付官方建议**轮询查询**（间隔 3–6 秒、总共约 60 秒）而不是依赖异步通知；
   超时必须紧接着调 `alipay.trade.cancel`；T+1 拉账单 CSV 与本地订单 diff 才能修单边账。
3. **从第一天起记账并按期申报**——金税四期 +《互联网平台企业涉税信息报送规定》之后，
   微信/支付宝支付数据已与税务系统联网比对，**私户收款不再是"查不到"的暗道**。
   《税收征管法》第 63 条构成偷税 → 追缴 + 滞纳金 + 罚款 50%–5 倍；
   《刑法》第 201 条逃税 10 万以上且占应纳税额 10% 以上 → 3 年以下。

### 5.5 给本项目的建议

**MVP 用方案 0（就是现在实现的 `manual` 渠道）**，同时并行启动两件事：
**域名 ICP 备案** + **个体工商户注册**（1–3 工作日、政府收费全免）。

跑通 PMF 之后再上**方案 1**（支付宝个人账号 + 电脑网站支付/当面付）——
2026 年支付宝新出的「支付集成 Skill / 商家入驻 Skill / 免注册免登录快速沙箱」
把个人做 Web 收银台的门槛压到了最低，这是个人最短路径。

如果同时面向海外用户，再并行开**方案 4**（Paddle）。

对应到代码：`billing.Channel` 接口就是为这个留的，
加一个支付宝渠道就是实现 `Name()` / `CreateCheckout()` 两个方法，
再补一个处理 `alipay.trade.precreate` / `alipay.trade.query` / `alipay.trade.cancel`
和 `bill.downloadurl.query` 对账的 worker。

## 6. 分发路线

| 路线 | 门槛 | 适合 |
|------|------|------|
| Chrome Web Store | 开发者账号 $5 一次性，审核 1–7 天 | 面向公众，需要过审 |
| 自建 CRX / 企业策略 | 无 | 内部团队、To B 客户 |
| 网页版（无插件） | 无 | 拉新入口，SEO |

**建议**：网页版和插件同期做，插件是加分项而不是唯一入口。
